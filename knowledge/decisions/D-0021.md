# Profile-named summons and explicit manual-spawn refusals

Rusty requested a clean summon command for the Face-Stealer and future creatures,
plus investigation of the apparently ineffective spawn egg. They explicitly chose
"Keep restriction; show a clear failure message" when the lifetime habitat rule was
identified. D-0020's territory constraint remains in force.

Each loaded profile gets a literal branch of `/summon` named by its resource ID, such
as `/summon aberrantmobs:face_stealer`. Optional coordinates and NBT follow vanilla's
syntax. Registration uses the current command-build registry context, so additional
profiles acquire their commands without another Java entity registration. Existing
entity IDs are not shadowed by profile aliases. The legacy `aberrantmobs:aberrant`
command remains available and receives the same validation. Operator permission is
retained. The shared entity type, save identity and selectors remain D-0001's design.

Eggs use vanilla's configured entity creation, then validate before adding the entity
and consuming the item. A habitat or Peaceful-difficulty refusal is reported to the
player and preserves the egg. Both block and source-fluid uses follow this rule.
Spawner configuration retains its existing vanilla path; spawner-produced creatures
still face the per-tick lifetime constraint. Named summons reject invalid habitat
before world insertion, including validation of any Aberrant passengers.

Real item-use tests reproduced the previous surface egg's success result; a valid
underground egg survived. The command dispatcher reproduced the missing named IDs.
Regression cases cover those paths, profile selection, coordinates/NBT, command
completion, permissions, a second data-only profile and the legacy command's refusal.
Publication and deployment require a separate release go.
